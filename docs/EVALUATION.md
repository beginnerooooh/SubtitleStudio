## 1. 结论速览

### 1.1 同口径对照（同样 10 分钟片段，唯一公平比较）

| 指标 | 改造前（v1 旧 pipeline） | 改造后（v2） | 提升 |
|---|---:|---:|---:|
| 行级完全匹配（文本+时间） | **0.7%** | **21.3%** | 30× |
| 文本逐字一致行 | 2.2% | **28.7%** | 13× |
| 时间达标行（±0.3s） | 2.9% | **31.6%** | 11× |
| 全文 CER | 48.5% | **34.4%** | −14.1pp |
| 字符召回（LCS） | 54.1% | **76.1%** | +22pp |
| 生成行数 / 参考行数 | 71 / 136 | 155 / 136 | — |

### 1.2 整片（50:38，需求口径）

| 指标 | v2 整片结果 |
|---|---:|
| 行级完全匹配 | **16.3%**（89 / 545） |
| 文本逐字一致行 | **21.5%**（117 / 545） |
| 时间达标行（±0.3s） | **29.5%**（161 / 545） |
| 全文 CER | **35.5%** |
| 字符召回 | **77.4%** |
| 成功配对 / 漏行 / 多行 | 480 / 65 / 214 |
| 起始时间中位误差 | **+0.009s** |
| 起始时间 ±0.3s 命中率 | **88%**（唯一文本配对的 93 行） |
| 结束时间 ±0.3s 命中率 | **98%** |
| 生成行数 / 参考行数 | 694 / 545 |
| 边界情况（需人工确认） | 200 条（上限截断） |

> 整片指标低于 10 分钟片段，是因为整片含大量唱歌与连麦段落
> （片段以说话为主）。时间轴精度（88%）反而更高，说明时间校正稳定。
> 注意 `ma_start_sec`（8.3s）这类「平均绝对误差」会被少量错配行
> 严重拉高，评估时间轴请用**中位数**与**±0.3s 命中率**。

**为什么不是 100%**：上限分析（`outputs/_eval/ceiling.py`）显示，
即使切行完美，**文本完全一致的行最多只能到 36.3%** —— 因为本地 ASR
（whisper-large-v3）对真人直播的识别本身有 27% 的字符错误：
`GT 4681 字 → 正确覆盖 3403 字（72.7%）`。剩余差距主要来自：

1. 口音/连读/口误导致的识别差异（约 27% 字符）；
2. 唱歌段落歌手咬字与伴奏掩蔽（错误率显著高于说话段）；
3. 人工校对的排版习惯（断行点、是否合并短句）。

**结论**：在"以 ASR 为唯一文本来源"的前提下，100% 精确匹配**不可达**；
当前实现已把可用性指标（行级完全匹配）从 0.7% 提到 21.3%（片段）/
16.5%（整片），并把时间轴做到与人工校对无系统性偏差。若要继续逼近
上限，必须引入**外部文本源**（歌词库、弹幕、或用户提供文稿）——
歌词链路已实现并验证（见 §3）。

## 2. 根因分析（实测，非推测）

每一项都由「改造前 → 改造后」的对照实验得出，实验脚本保留在
`outputs/_eval/` 下（`*.py`），可直接重跑。

### R1 引擎能力不足：small → large-v3

| 模型 | 字符召回 | 序列相似度 | 10 分钟解码耗时 |
|---|---:|---:|---:|
| whisper small（旧默认） | 0.598 | 0.659 | 14.8s |
| whisper large-v3 | 0.659 | 0.721 | 33.7s |

`large-v3` 文本与时间都更好，且**行时间能与人工校对对齐到 20ms 级**
（旧 small 偏差在 0.3~0.5s）。

### R2 VAD 过滤会吞掉歌声与弱起句

| VAD | 段数 | 字符数 | 召回 | 相似度 |
|---|---:|---:|---:|---:|
| 开（旧默认） | 127 | 941 | 0.649 | 0.710 |
| **关（新默认）** | 151 | 1098 | **0.770** | **0.783** |

faster-whisper 内置的 Silero VAD 把整段唱歌判为非语音后**直接跳过**，
「染个茶色」整段消失。改为关闭 VAD + 后处理剔除幻听（`_keep_segment`）。

### R3 整段解码会静默跳过 26 秒

同一份音频，只改分块大小：

| 分块 | 段数 | 字符数 | 召回 | >10s 的空洞 |
|---:|---:|---:|---:|---|
| 1200s（整段） | 142 | 1099 | 0.769 | 88→114s、156→171s、451→464s |
| 120s | 181 | 1408 | 0.823 | 88→105s |
| 75s | 178 | 1371 | 0.851 | — |
| 60s（新默认区间） | 187 | 1353 | **0.850** | — |

whisper 的长音频解码在遇到连续唱歌时会「提前收尾」，把随后 20~30 秒
直接跳过。**分块 + 块间重叠 + 独占区间去重**解决了这个问题。

### R4 时间戳系统性偏早

| 场景 | 起始误差中位数 | ±0.3s 命中率 |
|---|---:|---:|
| 直接用模型词时间 | −0.677s | 25% |
| 逐行「能量起振点」吸附 | −0.079s | 55%（但终点恶化） |
| **全片互相关校正（新方案）** | **+0.009s** | **88%** |

逐行吸附会饱和（对 −0.3s 与 −0.7s 给出相同结果），不可用。
最终采用**全片互相关**：把「字幕覆盖区间曲线」与「音频活动度曲线」
对齐，网格搜索最优平移量，增益 0.7（实测标定，0.6~0.75 区间平稳）。

### R5 切行粒度与人工习惯不符

旧实现「一个 ASR 段 = 一个字幕行」，人工校对是「一个语义语块 = 一行」：

| 指标 | 旧 | 新（DP 切行） | 人工校对 |
|---|---:|---:|---:|
| 行长中位数 | 13.5 字 | 8.2 字 | 9 字 |
| 行数 | 645 | 699 | 545 |
| 文本一致率 | 3.1% | **22.0%** | — |

新实现把切行建模为**最短路径问题**：代价 = 行长偏差² + 语义边界奖励
（句末标点/逗号/停顿）+ 时长约束，全局最优。标点由 `ct-punc` 模型
恢复后作为**切行线索**（不进入最终文本——人工样本本身不含标点）。

### R6 重复行

whisper 在歌声与回声上会重复生成同一句。加「短间隔（≤25s）且时间不重叠
的相同文本」去重，且**绝不修改保留下来的行的时间**（早期版本合并时间
导致出现 117 秒的超长行、破坏时间轴单调性）。

## 3. 方法评估（需求 8：找出效果最优的方法）

| 方法 | 中文直播文本质量 | 时间轴 | 速度 | 结论 |
|---|---|---|---|---|
| whisper small | 差（召回 0.60） | 偏差 0.3~0.5s | 34× RTF | ❌ 淘汰 |
| whisper large-v3 | **好（0.66→0.77 含分块）** | 好（校正后 ±0.01s） | 7.5× RTF | ✅ **默认** |
| FunASR paraformer-zh | 中（专名较好，语序错乱多） | 字级尚可 | 8× RTF | ⭕ 备选/对比 |
| FunASR SenseVoice | 差（漏标点、串词） | 无词级 | 慢 | ❌ |
| FunASR 时间戳预测（强制对齐） | — | 均匀铺开，不可用 | 快 | ⚠️ 仅用于无 LRC 时 |
| Demucs 人声分离 | 略降（分离伪影） | 无影响 | +27s/10min | ⭕ 默认关，BGM 重时开 |
| 关闭 VAD | **+11pp 召回** | — | 略慢 | ✅ 默认 |
| 60~120s 分块 | **+8pp 召回** | — | +15% | ✅ 默认 120s |
| 全片互相关时间校正 | — | **+41pp 时间命中** | 2s | ✅ 默认 |

**唱歌部分的处理结论**（需求 5）：
- Shazam 对直播翻唱**基本无效**（实测 3 个片段 0 命中）；
- 有效路径是「**ASR 文本 → 歌词库检索 → 用 LRC 行时间 + 行级匹配窗口
  定位本次唱到的段落**」。实测《七里香》段落：检索命中「七里香/周杰伦」
  得分 0.958，窗口定位到第 2~7 行（正是本次所唱），时间轴以 LRC 为基准
  偏移到演唱块起点；
- 强制对齐（`speech_timestamp_prediction`）在**整首歌词**上会均匀铺开
  （48 字撑满 4 分钟），因此只在没有同步歌词时作为近似。

## 4. 仍需人工确认的边界情况（需求 3）

评测报告会自动列出这些行（`outputs/_eval_last/report.md` 的
「仍需人工确认的边界情况」表）。按出现频率降序：

| # | 类型 | 表现 | 建议处理 |
|---|---|---|---|
| B1 | **文本近似** | 相似度 0.6~0.99 的错字/近音字（如「聚层」vs「沮丧」） | 听音频确认；可用歌词库纠错 |
| B2 | **漏行** | 参考有、生成无（当前 60/545 ≈ 11%） | 多为极短语气词（「嗯」「哎」）或歌声弱起 |
| B3 | **多行** | 生成有、参考无（214 条） | 多为识别差异导致的另一版本文本，非幻觉 |
| B4 | **时间偏移** | 单行起止差 > 0.3s | 多见于长停顿后的首句 |
| B5 | **歌曲段** | 歌词行与 ASR 行混排处 | 歌词库版本不一致时会整体错位，需人工确认曲目 |
| B6 | **说话人归属** | 连麦/观众语音 | 启用单目标声纹后自动剔除，未启用时按识别结果保留 |
| B7 | **行切分点** | 同一句在逗号处断/不断 | 人工习惯差异，不影响可读性 |

**判定标准（可复核）**：
- 文本：`归一去标点/繁简/全半角` 后**逐字相等**才算匹配；
- 时间：起止**同时** ≤ 0.3s 才算达标（字幕工具通行标准）；
- 完全匹配：文本与时间同时达标。

## 6. 本轮迭代（第二轮反馈）

针对「BGM 人声没过滤干净 / UI 闪动 / 要桌面端 / 弹幕 XML / 歌词多源 /
自动保存撤销草稿箱 / 清理无用文件」的改进与实测。

### 6.1 BGM 人声抑制：多因子 + 保守策略

**问题**：单纯声纹无法区分「主播跟唱」与「伴奏原唱」（音色都接近），
且 VAD 会把整段唱歌+说话合并成 20~30 秒长段，按段整块剔除会连带丢掉
主播的话（实测 155 行掉到 77 行）。

**做法**：VAD 段先切成 ~5 秒**子窗**逐窗判定，再多因子融合（`core/bgm.py`）：

| 因子 | 原唱/伴奏(中位) | 主播现场(中位) | 权重 |
|---|---:|---:|---:|
| 声纹相似度 | 0.39 | **0.69** | 1.00 |
| 伴奏存在度（低频+高频+谱平坦度） | **0.52** | 0.41 | 0.55 |
| 立体声侧信号 | **0.20** | 0.11 | 0.35 |
| 响度变异 | 0.43 | 0.51 | 0.10 |

**人工标注集上的分离度**（7 段原唱 vs 8 段现场）：
声纹 0.39 vs 0.69 完全可分；阈值 0.30~0.36 区间准确率 **1.00**。

**但子窗级（71 现场窗 vs 7 原唱窗）区分度明显下降**：
声纹 0.51 vs 0.42，最佳阈值准确率仅 **0.76**（保留率 0.80 / 剔除率 0.29）。

**结论与取舍**：不自动删除，默认策略 `mark`——
- 只把疑似原唱子窗记入右侧「BGM 复核」面板（含时间、声纹分、伴奏度、原因）；
- 用户确认后再处理；需要激进清理可切 `filter`（阈值 0.12，只删强证据）。

实测：`mark` 策略下 144 行（原 155 行）**完全匹配 22.8%**，
既不丢主播内容，又让 BGM 影响可定位、可复核。

### 6.2 歌词多源链 + 自动换源

新增酷狗（Kugou）歌词源，形成 NetEase / Kugou / LRCLIB 三源链，并支持自建服务。

实测《七里香》检索过程：
```
歌词源 netease：返回 6 条候选
netease 的最佳版本歌手为「Xai小爱」，与「周杰伦」不符，继续尝试其它源
歌词源 kugou：返回 6 条候选
已在 kugou 找到高置信版本（七里香/周杰伦，0.98），停止换源
采用歌词：七里香 / 周杰伦（kugou，得分 0.98）
```
> 若只看第一个源，会把翻唱条目的歌词铺进时间轴（行序与时长都不同）。

**修复的实际缺陷**：`song.py` 模块级漏了 `import json`，导致酷狗解析
全部抛 `NameError` 被 `except` 静默吞掉（表现为「有歌词却拿不到」）。
已修复，并新增「配置字段静态自检」测试防同类问题。

### 6.3 弹幕 XML：适配真实录播姬格式

真实文件（BililiveRecorder 2.20，1756 条弹幕 / 176 礼物 / 5 SC / 3 舰长 /
时长 3.83 小时）暴露并修复了三处缺陷：

| # | 缺陷 | 影响 | 修复 |
|---|---|---|---|
| 1 | 昵称误取 `p` 的第 8 段（恒为 0） | 所有用户名变成 "0"，热词失效 | 改读 `user` 属性 |
| 2 | 礼物/SC/舰长被当作弹幕文本猜测 | 礼物数 10（实际 176），SC 附言丢失 | 新增独立节点解析 |
| 3 | 点歌句式与门禁词不一致 | 「点一首X」「来首X」漏检 | 统一句式集合 |

修复后：弹幕 1756 · 礼物 176（含 3 舰长 5 SC）· **点歌请求 7 条**（发如雪、
简单爱、煎熬、樱花草、兰亭序…）· 主播名与标题正确解析。

### 6.4 UI 闪动修复

原因：生成过程中每 0.4s 重绘**整个**输出组（400 行日志文本 + 表格 + 文件列表），
进度条与日志栏来回重排。

修复：只推送**真正变化**的组件（状态文字 / 新增日志），其余用 `gr.skip()`；
日志只在长度变化时更新；表格与文件列表只在完成时更新一次。

### 6.5 桌面端（Electron）

`desktop/` 三栏布局，对标剪辑软件精简形态（只保留字幕与简单剪辑）：

- **零配置**：主进程自动 spawn `runtime/python.exe app/desktop_server.py`，
  不需要用户装 Python / 开浏览器 / 记端口；窗口关闭时后端一并退出；
- **视频联动**：`<video>` 走 `/api/media`（支持 Range），点击字幕行跳转、
  播放时高亮当前行、时间轴显示播放头；
- **编辑**：双击直接改文本/时间、Ctrl/Shift 多选合并删除、切分、新增、
  整片平移、自动质检；
- **便利功能**：自动保存（防抖 1.5s）、撤销/重做（60 步）、草稿箱、
  崩溃恢复（autosave.json）、缓存清理；
- **离线可用**：界面资源全部本地，不引 CDN。

**兼容性处理**（实测踩坑）：
- 环境存在 `ELECTRON_RUN_AS_NODE=1` 时 electron.exe 会退化为纯 Node，
  `ipcMain` 为 undefined → 启动脚本需清除该变量；
- 部分机器 GPU 子进程以 `STATUS_DLL_NOT_FOUND (0xC0000135)` 崩溃并终止
  整个应用 → 默认 `disable-gpu` + swiftshader 软件渲染
  （可用 `SUBTITLE_STUDIO_GPU=1` 强制硬件加速）；
- 高 DPI 缩放（实测 175%，168 DPI）会把 1463px 屏幕压成约 770 CSS px
  → 工具栏允许换行、窄视口下右侧面板改为可开关抽屉。

**自检模式**：`SUBTITLE_STUDIO_SHOT=<png>` 可无人值守地截图并上报真实
CSS 视口尺寸（实测 1338×721，`scrollWidth == innerWidth` 无横向溢出）。

### 6.6 后端 API 与端到端验证

`app/desktop_server.py`（标准库 HTTP，零额外依赖）13 项接口全部通过：
