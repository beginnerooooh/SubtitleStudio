# Subtitle Studio

[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](LICENSE)
[![Python](https://img.shields.io/badge/Python-3.10%2B-blue.svg)](https://www.python.org/)
[![Electron](https://img.shields.io/badge/Desktop-Electron-9feaf9.svg)](https://www.electronjs.org/)

**中文** · [English](README.en.md)

本地运行的直播 / 视频字幕生成与编辑工具。把录音或录像自动转成**可直接使用**的字幕，
并提供一个对标剪辑软件的轻量桌面端，在时间轴上逐句校对、切分与调时。

**核心特点**

- **完全本地**：识别、声纹、歌词对齐都在本机跑，不上传任何音视频
- **为直播优化**：处理唱歌、BGM 人声、多人闲聊等直播音频的典型难题
- **可校对**：生成结果与人工校对样本逐行比对，给出可解释的准确率指标
- **可编辑**：双轨时间轴 + 视频预览，字幕位置所见即所得

## 功能

### 识别

- **多引擎**：faster-whisper（large-v3 等）/ FunASR（paraformer-zh）/ 外部 HTTP 服务
- **分块解码**：长音频按块解码并带重叠，避免模型静默跳过整段内容
- **关闭 VAD**：直播中的歌声、弱起句容易被 VAD 吞掉，默认关闭
- **时间轴校正**：用全片互相关把字幕覆盖曲线与音频活动度对齐
- **智能切行**：按长度 / 标点 / 停顿做动态规划，输出符合阅读习惯的断句
- **热词增强**：从弹幕 XML 提取高频昵称与术语，喂给引擎降低专名错误

### 声纹与 BGM

- **单目标声纹**：只判断「这段是不是当前主播」，说话 + 唱歌双音色
- **多因子 BGM 判别**：声纹相似度 + 伴奏存在度 + 立体声侧信号 + 响度变异
- **默认只标注不删除**：子窗级区分度有限，激进删除会误伤主播内容，因此默认把
  疑似原唱的时间段与判定依据列出来，由用户确认

### 歌曲

四级链路，成本递增、命中即停：

```
弹幕/SC 点歌请求  →  本地歌词库  →  在线多源（NetEase / Kugou / LRCLIB）  →  识曲
```

在线多源支持**自动换源**：当某源的最佳版本与原唱歌手不符时，自动尝试下一个源。
也可接入自建歌词服务。

### 歌词库与文本校正

识别模型对**歌声**的准确率明显低于说话（发音拉长、伴奏干扰）。但歌曲文本是确定的，
因此提供一条独立于识别的校正链路：

```
歌词库（导入 .lrc / .txt / .srt，或按歌名+歌手在线拉取）
   ↓  按时间顺序与字幕做相似度匹配（允许有限跳跃）
   ↓  高置信匹配 → 用歌词原文替换识别文本
```

- **断句阶段就参考歌词**：字幕会在歌词的分句处断开，行的时间与长度跟着歌词走，
  比事后替换更自然
- **只替换「歌词明显更可靠」的行**：要求相似度达标且歌词不比识别文本短，
  避免丢掉识别到的额外内容
- **句内分隔用空格**：同一句内被迫分隔时插入空格，不引入逗号等标点

### 弹幕旁路校正

直播里，弹幕/礼物/SC 经常**重复主播刚说的话或专名**（观众刷屏复述、点歌、致谢）。
这些是「时间对齐的外部文本源」：

- **时间窗口加权**：同时刻附近弹幕权重更高（主播与观众反应几乎同步）
- **同音字纠正**：识别把专名念错时（如「翠翠沙」→「脆脆鲨」），用弹幕里反复出现的正确写法替换
- **只改行内文字，绝不动时间轴**：安全阀为「替换超过一半行数则整体放弃」
- 解析内容包含**用户 ID、昵称、礼物名、弹幕正文、SC 附言**

### 手动曲目清单

可手动填写本场直播中主播演唱的所有歌曲：

- 直接驱动歌词库检索，不必依赖识曲去猜
- 缩小 BGM 判定的搜索范围，**显著降低「把主播唱歌误判为 BGM 原唱」的几率**
- 作为断句的歌词来源，让字幕在正确的分句处断开

### 等待反馈

所有需要等待的操作都会弹出**居中进度窗口**：

- 全屏遮罩，等待期间点击不会重复触发（比逐个禁用按钮可靠，不会漏掉入口）
- 显示操作名、进度百分比与已用时间
- 操作超过 120ms 才出现，快速请求不会闪一下
- 同一时刻只允许一个任务，重复触发会提示"上一操作尚未完成"

覆盖：识别、导出、歌词拉取/导入、声纹提取、缓存清理、弹幕解析、
视频转码、项目保存与恢复。

### 视频格式支持

Chromium 只能播放它自带的容器（MP4 / WebM / Ogg）。对 **FLV、MKV、TS、AVI、WMV、RMVB**
等格式，后端会自动用 FFmpeg 转成带 `faststart` 的 MP4 并缓存：

- 优先 `-c copy` remux（20 秒素材约 0.1–2.4 秒完成，画质无损）
- 编码不兼容时退回转码
- 缓存按「路径 + 修改时间 + 大小」命名，二次打开秒开

### 编辑

- **双轨时间轴**：视频轨（胶片缩略）+ 字幕轨
- **拖拽调时**：拖动片段移动、拖边缘改起止（左线绿=起点，右线橙=终点）
- **批量框选**：空白处按住左键拖动框选，右键批量操作
- **时间码**：统一 `时:分:秒:帧`，帧率取自视频
- **字幕样式**：字号 / 颜色 / 描边 / 位置（预设或自由拖动）
- **便利功能**：自动保存、撤销重做、草稿箱、崩溃恢复、缓存清理

### 歌词库与关键词校正

**歌词库**（lyrics/）：导入 .lrc / .txt / .srt，或按歌名+歌手在线拉取。

匹配采用**局部连续段**评分，而不是全片平均——这是关键设计：

| 场景 | 全片平均（旧） | 局部匹配（现） |
|---|---|---|
| 纯歌词 3 行 | 0.836 ✓ | 0.836 ✓ |
| 3 行歌词混在 200 行闲聊中 | **0.006 ✗ 被否决** | **0.836 ✓ 命中** |

一首歌通常只占全片几分钟，按全片平均会把分数稀释到阈值以下，
导致整首歌被否决（实测反馈「匹配效果不行」的根因）。现在改为
在字幕里滑动寻找**一段连续命中**的区域，只在该区域内评估相似度。

**真实数据上的三个关键修正**（用 1014 行实际字幕 + 两首歌的 lrc 测出）：

| 现象 | 根因 | 修正 |
|---|---|---|
| 两首歌都匹配 0 分 | 一句歌词常被 ASR 切成 2~3 行字幕，按「一行对一行」比较时每行只覆盖歌词的一半 | 允许多行合并后再与歌词行比较（`_windows`） |
| 情歌只命中 8 处（实际 33 处可替换） | 副歌重复 2~3 次，而每句歌词只留 1 个候选，第二段副歌的最佳候选已被占用 | 每句保留多个候选；文字重复的歌词行不受顺序约束 |
| 歌词写到相邻错行（「让爱的人都沉默」→ 下一句歌词） | 合并时边删边改，导致前面（行号更小）的匹配偏移 | 先算出全部替换计划，再一次性重建列表 |

另外加了**实际相似度校验**：窗口可能把相邻字幕也拼进来，如果旧文本
与新歌词确实不相似（< 0.45），就不替换——避免写出无关内容。
最终在真实数据上做到「零可疑替换」。

**关键词字库**（keywords/）：填入主播昵称、术语、口头禅等专名。

- 识别阶段作为提示词（initial_prompt），让模型**一开始就写对**
- 生成后做一次纠正：支持 正确写法|误写1,误写2 的别名替换，
  以及整行模糊纠正
- 只改文本、不动时间轴

### 字幕样式与视频压制

- **样式作用域**：默认全局生效；可对选中行单独设置（行级覆盖），
  或用「应用到所有字幕」把当前样式固化到每一行
- **压制视频**：把字幕烧录进画面（硬字幕），样式与预览完全一致
  （字号/颜色/描边/位置），通过 ASS 滤镜实现，优先使用硬件编码

### 评测

生成后可与人工校对样本对比，输出：

- 行级完全匹配 / 文本一致 / 时间达标率
- 字符错误率（CER）、字符召回率
- **可达上限分析**（说明为什么 100% 不可能）
- 仍需人工确认的边界情况清单

## 快速开始

### 环境要求

| 依赖 | 说明 |
|---|---|
| Python 3.10+ | 本项目在 3.12 上验证 |
| FFmpeg | 音视频抽取与缩略图生成 |
| Node.js 18+ | **仅桌面端需要**（构建期），运行时不依赖 |
| NVIDIA GPU（可选） | 4GB 显存可跑 large-v3 int8_float16；无 GPU 会退到 CPU |

### 安装

```bash
git clone https://github.com/beginnerooooh/SubtitleStudio.git
cd SubtitleStudio

# 创建虚拟环境并安装依赖
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt

# 确认环境（会报告 GPU / FFmpeg / 可用引擎）
python tools/cli.py info
```

> 首次使用会自动下载模型。如需完全离线，可预先将模型放入 `models/` 目录，
> 具体路径见[配置](#配置)。

### 生成你的第一条字幕

```bash
# 从视频生成字幕
python tools/cli.py generate path/to/video.mp4

# 带参考字幕自动评测
python tools/cli.py generate path/to/video.mp4 --ref path/to/reference.srt

# 结果在 outputs/<视频名>/<时间戳>/ 下（srt / lrc / ass / vtt / json）
```

### 启动图形界面

**桌面版（推荐）**

```bash
cd desktop
npm install      # 首次安装 Electron
npm start
```

桌面端会自动拉起本地后端，无需手动装 Python 或记端口。

**网页版（Gradio）**

```bash
python launcher.py          # 浏览器自动打开 http://127.0.0.1:7860
python launcher.py --debug  # 保留控制台与 DEBUG 日志
```

## 工作方式

处理流水线（`app/core/pipeline2.py`）：

```
音视频输入
  → 音频抽取（16k 单声道 WAV）
  → 人声分离（可选）
  → 声纹 / BGM 分析（可选）
  → 识别（分块解码 + 独占区间去重）
  → 歌曲检测与歌词对齐（可选）
  → 切行（DP）+ 标点恢复
  → 时间轴校正
  → 去重 / 重叠修复 / 单调化
  → 导出 + 评测
```

**关键设计取舍**（均有实测支撑，详见 [docs/EVALUATION.md](docs/EVALUATION.md)）：

- **关闭 VAD**：Silero VAD 会吞掉歌声与弱起句，导致整段丢失
- **分块 + 重叠**：whisper 对长音频会静默跳过内容（实测跳过 26 秒）
- **BGM 只标注不删除**：子窗级判别准确率约 0.76，不足以自动删除
- **不使用标点做最终文本**：标点只作为切行线索，最终文本以识别结果为准

## 后端 API

`app/desktop_server.py` 提供本地 HTTP 接口（标准库实现，无额外依赖），
桌面端与网页端共用同一套逻辑。

| 接口 | 说明 |
|---|---|
| `GET /api/health` | 环境与可用引擎 / 歌词源 |
| `GET/POST/DELETE /api/projects[...]` | 项目 CRUD、保存、自动保存、撤销/重做、导出 |
| `POST /api/edit/<op>` | 无状态编辑：split / merge / delete / insert / update / retime_edge / copy / paste / duplicate / qc |
| `POST /api/generate` · `GET /api/jobs/<id>` | 异步生成任务与进度轮询 |
| `POST /api/evaluate` | 评测 |
| `GET/POST /api/lyrics/*` | 歌词源列表、检索、配置自建服务 |
| `GET /api/lyrics/library` | 歌词库列表 |
| `POST /api/lyrics/library/{add,fetch,remove}` | 导入 / 在线拉取 / 删除歌词 |
| `GET /api/lyrics/match` | 预览字幕与某首歌词的匹配结果 |
| `GET /api/media?path=` | 媒体流（支持 Range） |
| `GET /api/videoinfo?path=` | 帧率与时长（供时间码） |
| `GET /api/thumbs?path=` | 时间轴胶片缩略图 |
| `GET /api/danmaku?path=` | 弹幕摘要（主播 / 礼物 / 点歌 / 热词） |
| `GET/POST /api/cache/*` · `/api/drafts/clean` | 缓存统计与清理、草稿清理 |
| `GET/POST /api/profiles[...]` | 声纹列表、注册、删除 |

## 配置

默认值集中在 `app/core/config.py`，全部支持环境变量覆盖。常用项：

| 环境变量 | 默认 | 说明 |
|---|---|---|
| `SS_DEVICE` | `auto` | `auto` / `cuda` / `cpu` |
| `SS_MODELS_DIR` | `models` | 模型目录 |
| `SS_CACHE_DIR` | `cache` | 可再生成的中间产物 |
| `SS_OUTPUT_DIR` | `outputs` | 生成结果 |
| `SS_ASR_ENGINE` | `whisper` | 默认引擎 |
| `SS_LYRIC_PROVIDERS` | `netease,kugou,lrclib` | 歌词源顺序 |

模型放置约定：

```
models/
  ct2/<model>/            faster-whisper 模型（CTranslate2 格式）
  hf/                     HuggingFace 缓存（声纹 ECAPA、人声分离）
  modelscope/             ModelScope 缓存（FunASR、时间戳预测）
```

## 项目结构

```
app/
  app.py                 网页版界面（Gradio）
  desktop_server.py      桌面端本地 API（标准库 HTTP）
  core/
    pipeline2.py         流水线编排
    providers/           可插拔识别后端（whisper / funasr / external）
    segmenter.py         切行动态规划
    punctuate.py         标点恢复（仅作切行线索）
    timing.py            时间轴校正
    bgm.py               BGM 人声多因子判别
    song.py              歌曲检测 / 歌词多源检索 / 强制对齐
    streamer.py          单目标声纹（说话 + 唱歌双音色）
    lyrics_library.py    歌词库（导入/在线拉取）+ 与字幕的相似度校正
```

## 人声分离与声纹注册（UVR5）

本地装了 UVR5（Ultimate Vocal Remover 5）时可直接复用它的模型做
**区间人声分离**，用于声纹注册：

三种注册方式任选：

1. 在时间轴上**框选**一段主播单独说话/清唱的区间
2. 在左栏**手动输入**起止时间（支持 `690`、`11:30`、`00:11:30`、`00:11:30:15`）
3. **直接导入**已经分离好的干声文件（wav/mp3/flac/m4a…，自动转 16kHz）

流程：
点「注册」→ UVR5 的 MDX 模型分离出人声（去掉 BGM）→ 重采样到 16kHz
→ 提取 192 维声纹 → 保存

实测：20 秒区间全程约 20 秒（含分离+提取）。

**为什么自己实现而不调用 UVR5 本体**：UVR5 是 PyInstaller 打包的
单体程序，只能用图形界面，无法命令行调用。但它下载的模型是标准
ONNX 权重，可以直接加载——这样还能按需只分离选中的小段，
比 UVR5 GUI 的整文件处理更贴合「时间轴挑一段」的用法。

**实现要点（都踩过坑）**

| 现象 | 根因 | 正确做法 |
|---|---|---|
| Got invalid dimensions ... Expected: 3072 | 按 n_fft=2048 算出 1025 频点 | 从 session.get_inputs() 读实际形状（3072 频点 = n_fft 6144） |
| 分离结果近乎静音、频谱重心 13kHz | 多算一步「掩码 = \|out\|/\|in\|」 | MDX 是「谱到谱」映射，输出即人声谱 |
| 只有首尾几百毫秒有声音 | 分块重叠区直接赋值，未覆盖帧保持全零 | 幅度累加取平均 + 沿用原谱相位 |
| 声纹引擎报「无效音频区间」 | `enroll()` 的时间参数是秒，传 `1e9` 会被 `_cap` 判为越界 | 先取 WAV 实际时长再传 |
| 声纹引擎报「必须 16000Hz」 | MDX 要 44.1kHz | 分离后再重采样到 16kHz |

未安装 UVR5 时自动退化为直接用原音频注册（不报错）。

## 性能

处理 72 分钟 1080p60 直播录制的实测耗时（RTX 3050 Laptop 4GB）：

| 阶段 | 耗时 | 说明 |
|---|---|---|
| 音频抽取 | ~5s | FFmpeg 解复用，与视频编码无关 |
| **识别（ASR）** | **~6 分钟** | 占总耗时 85% 以上，是唯一值得优化的阶段 |
| 时间轴校正 + 导出 | ~2s | 纯 CPU 计算，可忽略 |

**已生效的优化**

- **eam_size=1（贪心解码）**：实测**又快又准**——ASR 从 445s 降到 247s，
  且 EXACT/TEXT/TIME/CER/召回**全部指标都更好**。原因是长音频直播里
  beam search 更容易陷入重复循环与幻听（beam 越大越倾向"凑通顺的句子"）。
- **chunk_seconds=120**：whisper 在长块上会静默跳过内容。实测同一素材
  用 1200s 分块时 CER 0.721，改用 120s 后降到 0.34。
- **预览转码用 540p30 代理**：1080p60 转码全片要 13 分钟、产物 910MB；
  540p30 只需 7.4 分钟、224MB。字幕校对只需看清画面与口型。
- **硬件加速**：优先 h264_nvenc（NVENC）编码 + -hwaccel cuda 解码，
  无 NVIDIA 显卡时自动退回 CPU 编码（libx264 veryfast）。
- **转码缓存跨进程复用**：缓存键用内容摘要（md5），**不用 hash()**。
  Python 的 hash() 按进程随机加盐，导致每次重启都重新转码（实测三次
  独立进程给出三个不同键）——这是"每次都要等半小时"的根因。
- **前段先放行**：长视频转码时先生成前 90 秒可播片段（约 12 秒完成），
  后台继续转完整版，用户无需等待。
- **时间轴以源文件时长为准**：代理片段只有 90 秒，若按它渲染时间轴，
  生成的字幕（覆盖整片）会完全对不上。

**验证过但未采用**

- **并行分块解码**：ThreadPoolExecutor(max_workers=2) 反而更慢
  （72s → 164s）。CTranslate2 的 GPU 推理已吃满算力，并发只增加争抢。
- **BatchedInferencePipeline**：要求提供 VAD 分段（与"必须关闭 VAD"
  的核心设计冲突），且时间戳相对片段起点，需要额外补偿逻辑，
  收益不确定而错位风险明确。

function foo() { ... }

                      # 浏览器加载: SyntaxError → 白板
`

因此仓库带了 	ools/check_js_structure.js，用

做**真正的编译**：

`ash

`

## 已知限制

- **100% 精确匹配不可达**：本地 ASR 对真人直播的字符正确率约 73%，
  即使切行完美，文本完全一致的行上限约 36%。继续逼近需要外部文本源
  （歌词库 / 弹幕 / 用户文稿）。
- **BGM 判别默认只标注**：子窗级声纹区分度有限，自动删除会误伤主播内容。
- **歌曲识别依赖网络**：在线歌词源需要联网；离线只能用本地歌词库。
- **弹幕 XML 目前覆盖 BililiveRecorder 2.x 格式**，其他平台需补充解析。
- **无 GPU 时速度较慢**：建议用 `medium` 或 `small` 模型。
